## 何時會觸發

使用者提出以下需求時應使用：

- 「幫我整合 Firecrawl / Notion / Slack / Linear」
- 「幫我安裝這個 API / CLI / MCP」
- 「確認 Codex 能不能使用這個工具」
- 「這個服務要走 CLI、API、MCP 還是 connector？」
- 「把某個外部服務接進我的助手或新專案工作流」
- 「先整理我的數位工具清單，不要安裝」
- 「先產生整合計畫，之後再做」

不應用在：

- 一般寫作或筆記整理。
- 一般簡報製作。
- 一般文件、試算表、圖片處理。
- 已經有明確 connector 可用且只是單次查詢的任務，除非需要驗證或設定整合。

## 工作流程

1. 先確認使用者真正要整合的服務與用途。
2. 確認目前 Agent 與作業系統：Codex / ChatGPT、Claude、AntiGravity、OpenCode；Windows 原生、WSL、macOS、Linux 與 sandbox 不共用 PATH、`.venv`、OAuth session 或設定檔。
3. 檢查目前是否已有 Codex connector、plugin、CLI、API 設定或 MCP。
4. 一次只接一個服務：接好、測通、記錄，再接下一個。
5. 先確認是「只產生計畫」、「稽核現況」或「實際安裝」，再用優先順序選最輕且穩定的路線：
   - Google Workspace 個資服務：Gmail／Calendar／Drive／Classroom 讀取優先使用 connector / plugin；需要寫入或細緻 scope 才評估 GCP OAuth。API key 不能讀取私人 Gmail／Drive／Classroom 資料。
   - Codex connector / plugin：適合 Gmail、Google Calendar、Google Drive、GitHub 等 Codex App 已支援工具。
   - 官方 CLI：適合 GitHub CLI、Firebase CLI、Heptabase CLI 等穩定命令列工具。
   - REST API + `{{SECRETS_DIR}}/<service>_api_key`：適合需要精準控制且 API 穩定的服務。
   - MCP：只有 connector、CLI、API 不適合，或 MCP 明顯更好時才使用。
   - 瀏覽器控制：最後手段，適合 UI-only 或本機前端驗證。
   - CLI-Anything fallback：上述路線都不適合，且目標軟體或 source repo 可被檢查、可包裝成真正呼叫後端的 CLI 時才使用。
6. 安裝前說明需要的權限與憑證：通道、鑰匙、OAuth scope、API key/token 儲存位置、撤銷或輪替方式。
7. 安裝或設定後做一個低風險實測；若有寫入權限，先用測試資料夾、測試看板、測試課程或測試資料庫。
8. 手動新增 MCP、plugin、connector 或全域 skill 後，重啟 Agent 或開新對話，再判斷工具是否載入。
9. 把結果記錄到專案整合計畫、AI 能幹清單、工具清單或 Obsidian 駕駛艙。

Codex 設定範圍固定為：

- 全域：`{{CODEX_HOME}}/config.toml`
- 專案：`<project-root>/.codex/config.toml`
- 不直接 symlink 不相容的設定檔；依功能轉成 Codex TOML 後再驗證

## 安全規則

- 不把 API key、token、密碼、OAuth secret、app password、admin credential 寫進：
  - GitHub
  - repo 檔案
  - `AGENTS.md`
  - skill 檔案
  - README / docs
  - 公開或可能同步的 Obsidian 筆記
  - 截圖或聊天摘要
- 若使用者貼出 secret，不要原文重複；只說明應放在哪個本機安全位置。
- API key 與 token 預設放 `{{SECRETS_DIR}}/` 的 snake_case 檔名；環境變數只作執行期載入，不把 repo `.env` 當長期主版。
- commit / push 前，先確認沒有 secret-bearing file 被納入。
- 需要服務權限時，優先選最小權限與 read-only。
- 能用 OAuth 或 provider-managed connector，就不要手貼長期 API key。
- 安裝社群 MCP 前先確認來源；不要安裝來路不明或低信任的 MCP server。
- 授權前先說清楚 scope，收尾時提醒不用的 token 要撤、API key 要限制用途、OAuth grant 可撤銷。
- 教學或學生資料預設去識別化，例如只用班級代號與座號，不把真實姓名寫入 repo 或公開同步筆記。

## 常見服務快查

| 服務 | 建議通道 | 鑰匙 / 授權 | 注意 |
|---|---|---|---|
| Obsidian | 本機檔案或 MCPVault 類 MCP | 免 API key，本機 vault 路徑 | vault 路徑要明確，不掃無關資料夾。 |
| GitHub | Codex / GitHub connector 或 `gh` CLI | OAuth / provider login | connector 與 CLI auth 分開驗證。 |
| Google Drive / Gmail / Calendar | connector / plugin 優先 | OAuth | API key 不能讀私人 Workspace 資料。 |
| Google Classroom | 讀取先試 connector；寫入用 GCP OAuth | OAuth | 發作業、學生名單、繳交狀態需謹慎 scope。 |
| NotebookLM | Codex NotebookLM tools 或 `nlm` CLI | 登入式憑證 | session 可能過期，失效時重跑 login。 |
| Firebase | CLI / MCP / project config | Firebase login 或服務設定 | 金鑰不可進 repo，規則要檢查。 |
| Supabase | 官方 MCP / API | API key / token | service-role key 不可放前端或 repo。 |
| Padlet | MCP / API | API token | token 要保管，權限與介面變動需重驗。 |
| Notion / 其他 SaaS | connector / plugin 優先，其次官方 MCP / API | OAuth 或 API token | 寫入前確認 workspace、page、database schema。 |
| 沒有現成工具的 GUI app / source repo | CLI-Anything harness generation | 通常是本機檔案權限 + 真實後端依賴 | 先在隔離 workspace 產生與測試，通過後才安裝。 |

## CLI-Anything fallback 指引

當完全沒有合適 connector、官方 CLI、REST API、MCP 或瀏覽器路線時，可以評估 `HKUDS/CLI-Anything`。

這不是跳過授權或跳過後端的工具，而是把「可被檢查的軟體或 source repo」包成 agent 可用的 CLI harness。適合 GUI 應用、本機軟體、open-source repo、內部 codebase，前提是可以找到真實 backend、headless mode、scripting surface、native project format 或可被測試的核心函式。

已讀來源：`HKUDS/CLI-Anything` commit `dc7392489222dbcc520817609290755d6dd8b0bb`。

採用順序：

1. 先查現成路線：connector / plugin、官方 CLI、REST API、MCP、瀏覽器控制。
2. 若都不適合，先查 CLI-Hub 是否已有 harness：
   - `pip install cli-anything-hub`
   - `cli-hub search <software-or-domain>`
   - `cli-hub info <name>`
   - `cli-hub install <name>`
3. 若 CLI-Hub 沒有合適 harness，才評估安裝 `CLI-Anything` 的 Codex community skill，讓 Codex 依其 `HARNESS.md` 對本機路徑或 GitHub URL 產生新 CLI。
4. 產生新 CLI 時先放隔離目錄，例如 `/private/tmp/<tool>-cli-anything` 或專案 `100_Todo/projects/<tool>-cli-harness/`。
5. 驗收前不要全域安裝；至少要確認：
   - generated command 有 `--help`
   - 重要命令支援 `--json`
   - package 可以 `pip install -e .`
   - installed command 可在 source directory 外執行
   - 測試包含 unit tests 與至少一個真實後端或真實檔案 E2E smoke test
   - generated `SKILL.md` 有寫清楚依賴、使用方式與 agent-safe JSON 輸出

不要使用 CLI-Anything 的情況：

- 目標是 private SaaS，但資料存取仍需要 OAuth / API 權限；CLI-Anything 不能繞過授權。
- 本機沒有真實後端軟體，也沒有可測的 headless / scripting / file-format 路線。
- 只是一次性 UI 操作，瀏覽器控制能安全完成。
- 尚未建立 test target，卻會碰 production data。

```bash

cat > 200_Reference/scripts/cli-anything/install_cli_anything.sh <<'CODEX_LAZYPACK_INSTALL_CLI_ANYTHING_SH'
#!/usr/bin/env bash

set -euo pipefail

CLI_ANYTHING_REPO="${CLI_ANYTHING_REPO:-https://github.com/HKUDS/CLI-Anything.git}"
CLI_ANYTHING_COMMIT="${CLI_ANYTHING_COMMIT:-dc7392489222dbcc520817609290755d6dd8b0bb}"
CODEX_HOME="${CODEX_HOME:-${CODEX_HOME}}"
PYTHON_TOOLS_ROOT="${PYTHON_TOOLS_ROOT:-$CODEX_HOME/python-tools}"
SOURCE_DIR="${SOURCE_DIR:-$PYTHON_TOOLS_ROOT/CLI-Anything}"
HUB_ROOT="${HUB_ROOT:-$PYTHON_TOOLS_ROOT/cli-anything-hub}"
BIN_DIR="${BIN_DIR:-$PYTHON_TOOLS_ROOT/bin}"
UV_CACHE_DIR="${UV_CACHE_DIR:-$PYTHON_TOOLS_ROOT/.uv-cache}"
PYTHON_VERSION="${PYTHON_VERSION:-3.12}"

log() {
  printf '[cli-anything] %s\n' "$*"
}

need_cmd() {
  command -v "$1" >/dev/null 2>&1 || {
    printf 'Missing required command: %s\n' "$1" >&2
    exit 1
  }
}

need_cmd git
need_cmd bash
need_cmd uv

mkdir -p "$PYTHON_TOOLS_ROOT" "$BIN_DIR" "$UV_CACHE_DIR"

if [[ -d "$SOURCE_DIR/.git" ]]; then
  log "updating source checkout: $SOURCE_DIR"
  git -C "$SOURCE_DIR" fetch --tags origin
else
  if [[ -e "$SOURCE_DIR" ]]; then
    backup="${SOURCE_DIR}.backup.$(date +%Y%m%d-%H%M%S)"
    log "source path exists but is not a git checkout; moving to $backup"
    mv "$SOURCE_DIR" "$backup"
  fi
  log "cloning $CLI_ANYTHING_REPO"
  git clone "$CLI_ANYTHING_REPO" "$SOURCE_DIR"
fi

git -C "$SOURCE_DIR" -c advice.detachedHead=false checkout "$CLI_ANYTHING_COMMIT"

skill_dir="$CODEX_HOME/skills/cli-anything"
if [[ -e "$skill_dir" ]]; then
  backup="${skill_dir}.backup.$(date +%Y%m%d-%H%M%S)"
  log "backing up existing Codex skill to $backup"
  mv "$skill_dir" "$backup"
fi

log "installing Codex cli-anything skill"
bash "$SOURCE_DIR/codex-skill/scripts/install.sh"

log "creating CLI-Hub virtual environment"
UV_CACHE_DIR="$UV_CACHE_DIR" uv venv --python "$PYTHON_VERSION" --allow-existing "$HUB_ROOT/.venv"

log "installing cli-anything-hub"
UV_CACHE_DIR="$UV_CACHE_DIR" uv pip install --python "$HUB_ROOT/.venv/bin/python" cli-anything-hub

log "writing cli-hub wrapper"
cat > "$BIN_DIR/cli-hub" <<EOF
#!/usr/bin/env bash
export HOME="$HUB_ROOT/home"
export CLI_HUB_NO_ANALYTICS=1
mkdir -p "\$HOME"
exec "$HUB_ROOT/.venv/bin/cli-hub" "\$@"
EOF
chmod +x "$BIN_DIR/cli-hub"

log "verifying Codex skill files"
test -f "$skill_dir/SKILL.md"
test -f "$skill_dir/references/HARNESS.md"
test -f "$skill_dir/references/commands/cli-anything.md"
test -f "$skill_dir/scripts/skill_generator.py"

log "verifying CLI-Hub"
"$BIN_DIR/cli-hub" --help >/dev/null
"$BIN_DIR/cli-hub" search image --json >/dev/null

log "installed"
log "source=$SOURCE_DIR"
log "commit=$(git -C "$SOURCE_DIR" rev-parse HEAD)"
log "skill=$skill_dir"
log "hub=$HUB_ROOT/.venv"
log "wrapper=$BIN_DIR/cli-hub"
log "restart Codex before expecting the new cli-anything skill to appear in fresh skill discovery."
CODEX_LAZYPACK_INSTALL_CLI_ANYTHING_SH
chmod +x 200_Reference/scripts/cli-anything/install_cli_anything.sh
```

## 跨 Agent 設定入口參考

這些入口變動很快，實作前請查目前官方文件或 app 介面。

| Agent | 連接器 / App 入口 | 手動整合設定 |
|---|---|---|
| Codex / ChatGPT | ChatGPT `Settings -> Apps` 或 `Plugins`，帳號可用時優先；自訂 MCP 可能需要網頁版 Developer mode | `codex mcp add`、`{{CODEX_HOME}}/config.toml` 或專案 `.codex/config.toml` |
| AntiGravity | IDE MCP Store 與內建 browser route | `{{GEMINI_CONFIG}}/mcp_config.json`，IDE / CLI 共用 |
| Claude Code / Desktop | Settings -> Connectors | `claude mcp add`、專案 `.mcp.json` 或 user config |
| OpenCode | 通常沒有 connector catalog | 專案 `opencode.json` 或全域 `~/.config/opencode/opencode.json` |

手動 MCP 注意：

- 新增或修改 MCP 後，完全重啟 Agent 或開新對話，再問「現在看得到哪些 MCP 工具」。
- Windows 原生 Claude Code 透過 `npx` 啟動 stdio MCP 時，通常要包 `cmd /c`：`claude mcp add <名稱> -- cmd /c npx -y <套件名>`。
- JSON 設定檔不能有註解或多餘逗號。
- Windows 路徑在 JSON 裡用 `C:/...` 或 `C:\\...`；單一 `\` 會壞。
- 遠端 MCP 出現 401 / 未授權，通常是 OAuth 未完成或過期，先重跑登入/授權流程。
- MCP 裝太多會吃上下文，導致工具選擇混亂；只保留本專案需要的工具。

## Firecrawl 範例

Firecrawl 適合用來抓取公開網頁內容、整理文章或研究資料。若已在本機跑通，不需要重新安裝，只要當次驗證。

驗證方式：

```text
請 Codex 使用 Firecrawl scrape https://example.com，確認回傳 Markdown 與 HTTP 200。
```

API key 原則：

- 只放在本機安全設定。
- 不上傳 GitHub。
- 不寫入 `AGENTS.md`、skills、README、docs 或 Obsidian 公開同步筆記。

## Notion 範例

Notion 優先走 Codex Notion plugin / connector。只有 plugin 不能完成的特殊 API 工作，才再評估 REST API + 本機 `.env` 或 MCP。

安裝與驗證方式：

1. 啟用 Notion plugin / connector。
2. 連接自己的 Notion workspace。
3. 用只讀方式驗證，例如讀取目前連線使用者資訊，或搜尋使用者指定的測試頁面。
4. 若要建立或更新頁面，先取得使用者明確確認。

## Core Rules

1. Confirm the user's actual use case before installing or configuring anything.
2. Integrate one service at a time: connect, verify, document, then move to the next service.
3. Separate the route into two decisions:
   - Channel: connector/plugin, MCP, CLI, REST API, or browser/computer control.
   - Credential: no key/local filesystem, API key/token, provider-managed login, or OAuth.
4. Before local MCP or CLI setup on a new machine, check the minimum runtime layer: `node --version`, `npm --version`, `git --version`, Python availability when the service needs it, and whether the target agent/account is logged in. Do not install runtimes silently; tell the user what is missing and why it is needed.
5. Treat Google Workspace personal-data services as a special case. Gmail, Calendar, Drive, and Classroom normally require connector/provider OAuth for personal data; an API key cannot read a user's private Google Workspace data. Use connector/plugin for simple reads, and consider a user-approved GCP OAuth project only for writes or fine-grained scopes.
6. Prefer the lightest stable route that fits the task:
   - Codex connector or plugin when Codex App already provides a safe first-party workflow.
   - Official CLI when the service has a stable CLI and commands are enough.
   - REST API plus a local secret loaded from `{{SECRETS_DIR}}/<service>_api_key` when precise read/write control is needed.
   - MCP only when connector, CLI, or API are not suitable, or when MCP gives a clearly better agent experience.
   - Browser automation only as a last resort for UI-only workflows or local frontend verification.
   - CLI-Anything harness generation only when no suitable connector, official CLI, API, MCP, or browser route exists and the target software/source repo can be inspected locally or from GitHub.
7. For current tool choice, verify live docs or the currently available Codex tools when the route may have changed. Connector catalogs and MCP stores move quickly; if the UI no longer matches the guide, trust the current product UI or official docs and record the drift.
8. Install or configure only what the user confirmed. Do not add adjacent tools because they seem useful.
9. Before OAuth, API key, token, write access, or browser-session use, explain what credential/scope is being granted, what it can access, and how to revoke or rotate it.
10. After setup, run one real, low-risk verification action. For write-enabled integrations, verify in a test target before touching production data.
11. Never write API keys, tokens, passwords, OAuth secrets, app passwords, admin credentials, or private keys into GitHub, repos, `AGENTS.md`, skills, public Obsidian notes, docs, README files, screenshots, or chat summaries.
12. If student or classroom data is involved, default to de-identified records such as class code plus seat number, not real student names.
13. If a global skill is added or changed as part of the integration, update the Obsidian global skill mirror note.
14. Keep Codex configuration scope explicit:

### New Machine Preflight

```bash

```

## 2. Route Decision

Think in two independent axes:

- Channel: connector/plugin, MCP, CLI, REST API, or browser/computer control.
- Credential: no key/local filesystem, API key/token, provider-managed login, OAuth, or service account.

The channel decides how the agent reaches the service. The credential decides how much authority is granted. Do not confuse the two: for example, MCP can be backed by OAuth, an API token, or local filesystem access depending on the service.

### Google Workspace First

Before applying the generic route order, check whether the target is a Google Workspace personal-data service:

- Gmail, Google Calendar, Google Drive, and Google Classroom personal data normally require OAuth or a provider-managed connector.
- A single API key cannot read a user's private Gmail, Drive, Calendar, or Classroom data.
- For simple read-only work, use the Codex/ChatGPT Google connector or available first-party app route when it fits.
- For write access, fine-grained scopes, or classroom operations such as creating assignments, consider a user-approved GCP OAuth project only after explaining the setup cost and scope.
- Service accounts are for server-to-server or delegated workspace use, not a shortcut into a user's personal Google account.
- Google-owned tools do not all use the same auth path: Firebase commonly uses CLI/project credentials or service configuration; NotebookLM commonly uses a login-style CLI/session route.

### Generic Route Order

Use this order:

1. Codex connector / plugin
   - Best when the connector already exists and handles auth safely.
   - Typical examples: Gmail, Google Calendar, Google Drive, GitHub.
2. Official CLI
   - Best when a stable CLI exists and the workflow is command-oriented.
   - Verify with a real command, not only `which`.
3. REST API + local environment
   - Best for precise read/write behavior and stable official APIs.
   - Store credentials outside tracked files.
4. MCP
   - Best when the service benefits from agent-native tools or no simpler route fits.
   - Keep MCP count small because every tool definition adds overhead.
5. Browser automation
   - Best for local frontend tests, UI-only services, or temporary verification.
   - Use logged-in browser automation only when the task requires the user's existing session.
   - Treat this as the last resort because it is slower and more fragile than connector, MCP, CLI, or API routes.
6. CLI-Anything harness generation
   - Use only when no suitable connector, official CLI, REST API, MCP, or browser route exists.
   - Best for GUI applications, local software, open-source repos, or internal codebases where the backend, native file format, or scripting surface can be inspected.
   - Not a shortcut around authentication, proprietary services, private data access, or missing backend software.
   - Build in a disposable workspace first, then install only after validation.

- user-wide MCP/config: `{{CODEX_HOME}}/config.toml`

## 5. CLI-Anything Fallback

Use `HKUDS/CLI-Anything` only as a fallback route when the integration problem is:

- "Codex needs a CLI for this software or repo."
- There is no suitable first-party connector, official CLI, stable API, useful MCP, or reliable browser route.
- The target has source code, a local install, native project files, scripting hooks, headless mode, or an inspectable backend that can be wrapped.

Decision sequence:

1. Search existing tools first: Codex connector/plugin, official CLI, API, MCP, browser route.
2. If none fits, search CLI-Hub before generating a new CLI:
   - `cli-hub search <software-or-domain>`
   - `cli-hub info <name>`
   - install only the one needed harness, not a broad matrix, unless the task requires a workflow matrix.
3. If no existing harness fits, consider installing the `cli-anything` Codex skill from the repo and using it to build a new harness from a local path or GitHub URL.

   - generated command has `--help`

- The target is a private SaaS where data access still requires OAuth/API permissions. CLI-Anything cannot bypass auth.
